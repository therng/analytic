## Summary

The desktop 3-column grid is architecturally sound with well-structured grid areas and token-driven spacing. Main risk areas are silent content clipping in col1/col2 (overflow:hidden with no scroll fallback), two hardcoded pixel values that don't respond to breakpoint tokens (botpnl height + radar height), and a redundant nested @media rule. View toggle label "Open" is semantically ambiguous.

## Critical Issues

### Issue 1: dc-left and dc-middle silently clip overflow content

**Severity:** Critical
**Location:** `globals.css:3361–3370` (`.dc-left, .dc-middle, .dc-right` base rule)
**Category:** Usability / Visual

**Problem:**
Both `dc-left` and `dc-middle` use `overflow: hidden`. Col1 contains gauges row + DD metrics (4 chips) + radar chart (200px fixed) + spacing. At 1024px viewport height the combined content (~380–420px) can exceed available row 1 height after botpnl (240px) + heatmap (~110px) are subtracted, causing silent clipping with no scroll affordance.

**Impact:**
Radar chart or DD extension chips get cut off at 1024px height. Users lose data without any visual cue that content is missing.

**Recommendation:**
Change `overflow: hidden` to `overflow-y: auto` on `dc-left` and `dc-middle` while keeping `scrollbar-width: none` to hide the scrollbar visually. Content remains accessible via scroll without visual clutter.

```css
/* Before */
.dc-left,
.dc-middle,
.dc-right {
  overflow: hidden;
  scrollbar-width: none;
}

/* After */
.dc-left,
.dc-middle {
  overflow-y: auto;
  overflow-x: hidden;
  scrollbar-width: none;
}
```

## Major Issues

### Issue 2: dc-botpnl height is a magic number — not token-driven

**Severity:** Major
**Location:** `globals.css:3395` (`.dc-botpnl { height: 240px }`)
**Category:** Code / Visual

**Problem:**
`240px` is hardcoded directly. The spacing system uses CSS custom properties (`--dc-pad-x`, `--dc-chart-h`, etc.) that scale per breakpoint. The botpnl band does not participate in this system, so it stays 240px at 1440p, 1920p, and 4K while surrounding elements scale.

**Impact:**
At 1920px the botpnl band looks proportionally small relative to the scaled columns. At 4K it becomes disproportionately compact.

**Recommendation:**
Introduce a `--dc-botpnl-h` token on the card and override per breakpoint.

```css
/* globals.css — token definition (base 1024px block) */
.dashboard-section > .account-card.account-card--desktop {
  --dc-botpnl-h: 240px;
  /* ... existing tokens ... */
}

/* botpnl rule */
.dc-botpnl {
  height: var(--dc-botpnl-h);
}

/* 1440px override */
@media (min-width: 1440px) {
  .dashboard-section > .account-card.account-card--desktop {
    --dc-botpnl-h: 260px;
  }
}

/* 1920px override */
@media (min-width: 1920px) {
  .dashboard-section > .account-card.account-card--desktop {
    --dc-botpnl-h: 280px;
  }
}
```

### Issue 3: Nested redundant @media inside 2560px block

**Severity:** Major
**Location:** `globals.css:3607–3609`
**Category:** Code

**Problem:**
Inside `@media (min-width: 2560px) { ... }`, there is another `@media (min-width: 2560px) { .dc-extra { grid-row: 1 / span 3; } }`. This double-nesting is a redundant no-op: the inner query is already guaranteed true by the outer. The rule works coincidentally but creates confusion and could break if the outer query changes.

**Impact:**
Maintenance trap — a future developer editing the breakpoint would need to update both wrappers. Also adds unnecessary CSS specificity nesting.

**Recommendation:**
Move the rule directly inside the outer `@media (min-width: 2560px)` block without the redundant inner wrapper.

```css
/* Before */
@media (min-width: 2560px) {
  /* ... grid rules ... */

  @media (min-width: 2560px) {
    .dc-extra { grid-row: 1 / span 3; }
  }
}

/* After */
@media (min-width: 2560px) {
  /* ... grid rules ... */
  .dc-extra { grid-row: 1 / span 3; }
}
```

### Issue 4: radarHeight prop hardcoded to 200px in JSX

**Severity:** Major
**Location:** `DashboardClient.tsx:682` (`<PerformanceQualityPanel variant="radar" radarHeight={200} ...`)
**Category:** Code / Visual

**Problem:**
`radarHeight={200}` is a pixel value embedded in JSX. At 1920px and 4K viewports the radar chart remains 200px while everything around it scales via `--dc-chart-h` and CSS tokens. There is no mechanism to scale this value with breakpoints from CSS.

**Impact:**
At larger viewports the radar looks proportionally small. At smaller viewports (1024px tight height) combined with the critical clipping issue above, 200px is a significant fraction of available col1 space.

**Recommendation:**
Either pass the radar height via a CSS variable using a ref measurement, or replace the hardcoded prop with a responsive value:

```tsx
// Simplest fix: scale with viewport
const radarHeight = isDesktop ? Math.min(200, window.innerHeight * 0.2) : 200;

// Or use a CSS container query approach — let PerformanceQualityPanel
// read its own height via CSS and remove the radarHeight prop entirely
<PerformanceQualityPanel variant="radar" radarHeight={200} ... />
// → remove radarHeight prop; let the component fill available space
```

## Minor Issues

### Issue 5: BotPnL empty state wastes the full 240px band

**Severity:** Minor
**Location:** `BotPnLPanel.tsx:245–251`
**Category:** Visual

**Problem:**
When no bot activity exists for the timeframe, the BotPnLPanel renders a centered "No bot activity for this timeframe." text in a 240px tall band. This is a large empty region that disrupts the visual rhythm between col1/col2 and the heatmap.

**Impact:**
Jarring dead space for accounts that trade manually (no bots). The heatmap appears disconnected from the columns above.

**Recommendation:**
When `bots.length === 0`, collapse the dc-botpnl band with `display: none` or reduce it to a minimal height (e.g. 32px with a single-line message).

```css
/* globals.css */
.dc-botpnl:has(.bot-pnl-panel--empty) {
  height: 32px;
  display: flex;
  align-items: center;
}
```

### Issue 6: Skeleton heights are magic numbers

**Severity:** Minor
**Location:** `DashboardClient.tsx:624–626` (`style={{ height: 80 }}`, `{ height: 60 }`, `{ height: 200 }`)
**Category:** Code

**Problem:**
Skeleton placeholder heights (80px, 60px, 200px, 120px) are inline magic numbers that don't match the actual rendered heights of their corresponding components. If component heights change, skeletons silently mismatch, causing layout shift.

**Recommendation:**
Define skeleton heights as CSS classes with values tied to the components they represent:

```css
.skeleton-chart--gauges  { height: 72px; }   /* matches donut row */
.skeleton-chart--metrics { height: 52px; }   /* matches kpi-detail-grid */
.skeleton-chart--radar   { height: 200px; }  /* matches radarHeight */
```

```tsx
<div className="skeleton-chart skeleton-chart--gauges" aria-hidden="true" />
<div className="skeleton-chart skeleton-chart--metrics" aria-hidden="true" />
<div className="skeleton-chart skeleton-chart--radar" aria-hidden="true" />
```

## Suggestions

### Suggestion 1: View toggle label "Open" → "Positions"

**Location:** `DashboardClient.tsx:861–876`

"Open" as a button label is ambiguous — it reads as a verb ("open this") rather than a noun ("open positions"). "Positions" is unambiguous and matches the data it reveals.

```tsx
// Before
<button ...>Open</button>

// After
<button ...>Positions</button>
```

---

### Suggestion 2: dc-left overflow-y: auto enables graceful degradation

**Location:** `globals.css:3361–3370`

Even after fixing Critical Issue 1, consider making `dc-left` scrollable as a resilience pattern. The column contains 3 independently-loading sections (gauges, DD metrics, radar). As features are added, overflow is likely to recur. Defensive `overflow-y: auto` + `scrollbar-width: none` means users always see all content without the dev team needing to track exact pixel budgets.

## Positive Observations

- **CSS token architecture** — `--dc-pad-x`, `--dc-pad-y`, `--dc-gap`, `--dc-chart-h` as custom properties on the card element with per-breakpoint overrides is an excellent pattern. Breakpoint blocks are additive and minimal.
- **Grid area naming** — `left`, `middle`, `right`, `botpnl`, `heatmap`, `extra` are semantically meaningful and easy to track across breakpoints.
- **`dc-right` spanning all 3 rows** — col3 correctly uses `grid-row: 1 / span 3` so it occupies full card height independent of how many rows are added below col1/col2.
- **`auto-fit` for metrics grids** — `repeat(auto-fit, minmax(0, 1fr))` on `.dc-metrics-grid` elegantly handles 3-chip and 4-chip rows without separate CSS rules.
- **Cascading API loading** — detail API calls gated on `overview.data` prevents N×3 flood on mount.
- **`aria-label` on all extension grids** — "DD extension", "Gain extension", "Trades extension", "Open extension" provide good screen reader landmarks.
